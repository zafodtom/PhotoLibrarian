# PhotoLibrarian 1.2.6-dev.2 — JPEG anonymization and backup policy

Second development prerelease following stable **PhotoLibrarian 1.2.5**. Supersedes **1.2.6-dev.1** and includes its JPEG trailer fixes plus the follow-up changes below.

## JPEG anonymization

- Fix the **Anonymize photo metadata** command for older camera JPEG files containing vendor-specific metadata appended after the JPEG end-of-image marker (EOI). These photos were previously skipped with the warning `JPEG has nonstandard appended data`, leaving their EXIF metadata unchanged.
- For a JPEG with a small appended metadata trailer, discard the trailer and the ordinary EXIF/IPTC/XMP/comment metadata without recompressing the existing JPEG scan.
- Retain the safety checks that **skip** multi-picture JPEG (MPF), an identifiable second JPEG/PNG/WebP, appended video (AVI/MP4/MOV-style containers) and unrecognized oversized trailers above 256 KiB. These cases are reported, not silently changed.
- The anonymization service continues to validate the rewritten file through the Windows image decoder and to use the existing original-photo/XMP backup, rollback and catalog-metadata cleanup path.

## Changes since 1.2.6-dev.1

- **Context menu:** `Anonymize photo metadata…` no longer retains permanent copies of the source photos or XMP. A temporary rollback copy protects against processing or database failures; it is deleted after successful completion or successful recovery. If recovery/deletion fails, the app reports the remaining copy as a critical issue instead of silently keeping personal metadata. **Album Settings** retains its optional backup checkbox.
- More precise JPEG trailer detection: `ftyp`, `RIFF` and `FF D8` bytes are not sufficient on their own to claim an appended image/video. The code validates plausible JPEG headers and EOI, PNG IHDR and container signatures before rejecting an image.
- Skipped JPEGs now report whether the trailing content looks like a second JPEG, PNG, WebP/AVI, MP4/MOV/HEIF-style media, or oversized unclassified data (with byte count).
- Files with actual MPF multi-picture metadata, recognizable secondary media or large unknown trailers are **still deliberately skipped** to avoid losing additional image/video payloads.
- The uploaded `IMG_0097.JPG` in the related bug report was inspected: its uploaded bytes contained one JPEG ending exactly at EOF, with a color profile but no EXIF/trailer. That upload cannot establish what the local source file contained at the time of the skip. Test with the unmodified disk copy before drawing conclusions.

## Backup policy for individual vs. album actions

- **Individual photo actions do not create permanent backup copies.** This includes context-menu **Clear all tags**, context-menu **Anonymize metadata**, single-image 90° rotation, and applying/saving changes in the image editor.
- Bulk album actions (**Clear tags/flags**, **Anonymize entire album**, and **Convert album to JPEG**) continue to honor their backup settings; retained backups remain optional where previously available.
- Existing historical backups under the user's AppData or `.album` are **not automatically deleted**. The editor's legacy **Revert** control remains available only when a matching historical original exists; new single-image edits do not enable it.
- Short-lived staging/rollback files may still be used for safe file replacement. They are deleted after a successful operation or successful restoration; a recovery failure is reported rather than silently destroying its only recovery copy.
- Embedded metadata transcoding now stages the completed image in a same-directory temporary file before replacing the source instead of truncating the live file, because individual tag writes no longer rely on retained backup originals.

## Privacy result dialogs

- After an anonymization operation, the cinematic dialog is now explicitly labelled **PRIVACY REPORT // PHOTO** or **PRIVACY REPORT // ALBUM**, instead of incorrectly displaying **USER CONFIRMATION // ALBUM**.
- The footer says the operation is finished, not that the user should confirm it.
- When no photo has been anonymized, the result explicitly says so rather than implying that backups of modified photos were created.
- A partially successful operation still uses the yellow warning treatment and reports cleaned, skipped and failed counts.

## Verification and limitations

- Windows CI on the latest code commit passed: **362 total tests, 357 passed, 0 errors, 0 failed, 5 not run** ([Windows CI run 43983295699](https://github.com/zafodtom/PhotoLibrarian/actions/runs/43983295699)).
- Regression tests cover camera-style JPEG metadata trailers, preserved encoded picture bytes, MPF/multi-picture JPEG, appended video, oversized unknown payloads and privacy-result dialog text.
- The actual user's file `100_2706.jpg` was **not provided for inspection**. Its exact trailer structure is unknown, so it must be tested on a **copy** before using the operation on the original.
- Anonymization is metadata cleanup, not forensic secure deletion. Retained backups, filesystem and system caches, names and photo pixels may still contain personal information.
